Course Enrollment: Payment Succeeded but No Record Created

A detailed explanation of the issue where customers were charged for course enrollments but no enrollment record appeared in the system — requiring manual admin intervention.

First observed: June 18, 2026  ·  Fully diagnosed: June 27, 2026  ·  Fix deployed: June 28, 2026

What happened?

Several customers completed a course enrollment checkout — their credit card was charged, and they saw a "success" screen — but no enrollment record was created in our database. The customer appeared to have no enrollment, received no confirmation email, and had no door access code. The admin had to manually enrol each affected customer.

This affected approximately 13 checkout sessions between June 18 and June 27, 2026. All payments were legitimate charges that landed in Stripe — the money left the customer's card — but from Open24's perspective the enrollment "never happened."

How course enrollment normally works

When a customer checks out for a course, the primary path handles enrollment creation directly in the browser:

Primary path (browser-driven):
Customer clicks "Pay" → Stripe charges the card → Browser is redirected back to Open24 → The page calls our server to say "payment confirmed, create the enrollment" → Record saved → Confirmation email sent.

This primary path is responsible for the vast majority of enrollments and works instantly. However, it depends on the customer's browser completing a round-trip — which can fail if the customer closes their tab, loses network, or their phone goes to sleep mid-redirect.

To guard against those edge cases, a safety net was added: a server-to-server webhook where Stripe independently notifies our backend that a payment succeeded. If the primary path missed the enrollment, the safety net catches it within seconds — no customer action required.

Safety net (server-to-server webhook):
Stripe sends a notification directly to our server ("this payment succeeded") → Backend checks if the enrollment was already created → If not, creates it now → Confirmation email sent.

In this incident, the primary path had a bug that caused it to silently fail for certain customers. The safety net — which was specifically designed to catch exactly this scenario — had not yet been connected to production due to a configuration oversight. The combination meant affected enrollments were permanently lost until an admin manually intervened.

Root Cause  Primary path silently skipped the enrollment

The problem

When a customer pays with a credit card that requires extra verification (3D-Secure — very common with Canadian and European banks), the browser is briefly redirected to the bank's verification page and then sent back to Open24. Upon return, the checkout page needs to load two things before it can finalize the enrollment:

  • Course data — what course the customer enrolled in (loads fast, ~18 records)
  • Session schedule data — which specific class sessions exist for that course (loads slower, ~500 records)

The code that handles the 3D-Secure return was waiting for the course data to load but was not waiting for the session schedule. On a fast connection this was never noticeable — both loaded within milliseconds. But on mobile networks or when the server was under load, the session data arrived a fraction of a second later.

The result: the system looked up "which sessions should this customer be enrolled in?" and found zero (because the schedule hadn't loaded yet). It then silently decided there was nothing to do — no error was shown, the success screen displayed, and the customer's pending checkout data was cleared from their browser. Permanently lost.

Fix applied

  • The return handler now waits for both course data AND session schedule data to be fully loaded before attempting to finalize — exactly like the normal checkout path already did.
  • If an item resolves to zero sessions (which should never happen for a paid course), the system now raises an explicit error instead of silently skipping it. This makes the problem immediately visible to the customer AND allows the webhook safety net to recover it.
  • The customer's pending checkout data is now only cleared after at least one enrollment record is confirmed saved — so a transient failure is recoverable on page reload.

Safety Net  Webhook safeguard was not yet connected to production

Context

The safety net was added specifically to protect against failures like the one above — any scenario where the browser doesn't finish its job (tab closed, phone lost signal, 3D-Secure redirect didn't complete cleanly). It was fully built, tested, and deployed in the codebase. The code worked correctly.

However, a configuration oversight meant the safety net was never actually receiving notifications from Stripe in the production environment:

  • The deployment script listed the Stripe payment key but omitted the webhook signing secret.
  • Every time the server was deployed, any manually-added webhook secret was overwritten with a blank value.
  • Without the signing secret, the webhook endpoint rejects all incoming requests for security reasons (it cannot verify they came from Stripe).
  • Additionally, the webhook URL had not yet been registered in the Stripe Dashboard for the live/production environment.

Had the safety net been connected, it would have caught every single one of the affected enrollments within seconds — automatically and without any customer or admin action. The primary path bug would have been invisible to customers.

Fix applied

  • The deployment script now includes the webhook signing secret alongside the payment key, so it survives every deploy going forward.
  • Operational documentation has been updated with step-by-step instructions for registering the webhook endpoint in the Stripe Dashboard and verifying it works.
Operational step required: The webhook endpoint must be registered in the Stripe Dashboard (live mode) and the signing secret must be saved to the production environment. This is a one-time setup task — once done, the safety net is permanently active.

Impact and recovery

Affected customers: ~13 checkout sessions across approximately 5–6 customers between June 18–27, 2026. All were manually enrolled by an admin within minutes to hours of reporting.

Financial impact: Zero. All payments were legitimate and matched to the correct customer. No refunds were needed — the enrollments were fulfilled manually.

Recovery of stuck records: Once the webhook is live, Stripe can "resend" the original payment-success events for any still-pending rows, which will automatically trigger the enrollment creation through the normal webhook flow. Alternatively, an admin can manually drain them via the existing admin-enroll tool.

Why wasn't this caught sooner?

  • The race condition was timing-dependent. On fast connections (like desktop on Wi-Fi — which all internal testing used), both data sources loaded within the same event loop tick. The bug only manifested on slower mobile connections or when the session count was high enough to create a perceptible load delay.
  • The "success" screen showed even on failure. Because the skip was silent (no error thrown, no UI feedback), the customer had no reason to suspect anything went wrong until they checked their enrollment list or didn't receive a confirmation email.
  • The safety net was assumed to be working. Since the webhook code was deployed and the route responded to requests, there was no obvious signal that it wasn't receiving real events from Stripe. The missing signing secret was invisible in normal operation — it only manifested as "zero events received," which could easily be confused with "no events to receive."

What prevents this from happening again?

  • Primary path fixed. The root cause — the data-loading race condition — is resolved. The checkout return handler now waits for all required data before acting, eliminating the silent skip entirely.
  • Safety net as a permanent backstop. Once the webhook is connected, every paid checkout has a guaranteed server-side path to enrollment creation — completely independent of what happens in the customer's browser. Tab closed? Phone died? 3D-Secure took too long? The webhook catches it within seconds.
  • Fail-loud, not fail-silent. If the primary path encounters any unexpected state (like zero sessions for a paid course), it now shows an error to the customer and preserves the pending data for retry — rather than silently succeeding with nothing saved.
  • Operational monitoring. The pending enrollments table serves as a clear health indicator: any row stuck in "pending" status for more than a few minutes means something is wrong. Admin can check this at a glance.
  • Deploy-proof configuration. The webhook secret is now part of the automated deploy pipeline — it cannot be accidentally erased by a routine deployment.
